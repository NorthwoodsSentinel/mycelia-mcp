**2.1 `workflow-gate`.** It parses each workflow with the `yaml` package and reads only executable positions: `run:`, a custom `shell:` (step, and `defaults.run.shell` at workflow and job level), and the values of `env:`, `container.env:` and `with:`. Aliases are resolved. A parse error throws. Rules that apply: the Inspector's rule 1 (a package manager's `run` of a `local:*` script), including a name spelled through an expression or a shell variable (`local:${{ … }}`, `local:$TASK`). Its rules 2 to 4 are not ported: there is no browser smoke and `SMOKE_BROWSER` appears nowhere in this repo (Measured). Kept from the sibling: a `uses:` that starts with `./` is a finding, because the walk does not enter that file. This repo has no `.github/actions/` (Measured), and `verify-action-pins` here already reports a local ref, so two guards report it; it is kept so the logic stays the reviewed one. The enforcing test is `scripts/lib/workflow-gate.test.mjs`: table cases, then a scan of every `.yml` and `.yaml` file in `.github/workflows/`, failing if the directory lists none. It joins `test:scripts`. That list is explicit, and a test in `scripts/verify-skills.main.test.mjs` fails when a tracked test-named file under `scripts/` is missing from it. `test:scripts` runs inside `test`, the last stage of `validate`, so the scan runs in CI and locally. Measured: the sibling's file reports 0 findings over both workflows (9 and 24 executable regions).

**2.2 `verify-install-fresh`.** It reads `bun.lock` through `scripts/lib/bun-lock.mjs` (JSON with trailing commas; `lockfileVersion` 1 only; anything else throws). A `packages` key is an install path of package names, one per `node_modules` level; a segment starting with `@` takes the next segment with it. The entry's first element is `name@version`, split at the last `@`, and the name must equal the key's last name. The required set is a walk from the root workspace: `dependencies` and `devDependencies` are required edges, `optionalDependencies` optional ones. An entry's `dependencies`, and its `peerDependencies` not named in `optionalPeers`, are required edges. An edge from the entry at `p1/…/pk` to `d` resolves to the first existing key among `p1/…/pk/d`, …, `p1/d`, `d`. A target reached only by optional edges is required when its `os`, `cpu` and `libc` admit this host. Only present entries are walked further. It fails on `stale` (the installed `package.json` version differs), `missing` (required and absent), a required edge to a name the lock does not hold, and unreadable metadata. It is first in `validate` and its failure names `bun install --frozen-lockfile`. Measured with the sibling's file: 284 entries parse, 253 are required on this host and all match. The 31 absent entries are exactly the ones the walk does not require: 25 platform builds of two packages, and 6 packages that no present package requires.

The probe was run before any code for this piece was committed, and it failed. The decision came back here, as section 3 required.

Measured in scratch projects outside this repo, with Bun 1.3.14 (the CI pin, installed from the `bun` npm package) and Bun 1.4.4. `esbuild@0.27.2` has a `postinstall` and is trusted by Bun's default list; `core-js@3.39.0` has one and is not.

| absent | 0 (esbuild trusted by default) | 0 |
| `["core-js"]`, both packages installed | names esbuild | names esbuild |
| `["esbuild"]`, both packages installed | names core-js | not run |

So a non-empty list replaces the default list on both versions, and an empty list does so only on 1.4.4. On the pinned Bun, `[]` is the same as no field.

So the only list that states this repository's decision is the empty one.

- What stands in for it today: CI installs with `--ignore-scripts` (Read, `main.yml`), and nothing in the tree has a script to run.

The `local-dev` skill gains this rule (section 5).

## 3. Tests: what each guard must fail on

- **workflow-gate.** Findings: `run: npm run local:gate`; `npm run local:dco`; a new `local:anything` inside a multi-line `run: |`; `bun run local:gate`; `npm run local:${{ matrix.task }}`; a custom `shell:` template that runs one; a `run:` reached through a YAML alias; `uses: ./.github/actions/x`. Also findings, by choice: `echo "npm run local:gate"` and `npm run validate # npm run local:dco` (section 4). Clean: `npm run validate`; a `local:` string in a YAML comment, a comment-only shell line or a step `name:`; `curl https://local:8080/`. Fail closed: unparseable YAML throws and names the file; zero workflow files fails. Then the live scan of this repo's two workflows.
- **install-fresh.** A version mismatch is `stale`. An absent required package is `missing`, from `dependencies` and `devDependencies` alike. Keys `@s/n`, `a/b` and `a/@s/n` resolve at the right directory, present and absent. Absent, optional and excluded by `os`: exempt. Absent, optional and the host matches: `missing`. `libc` separates two builds of one `os` and `cpu`. A package that a present package requires is `missing` whatever its platform fields say. Two locked versions of one name are told apart by path. Fail closed: a malformed lockfile, another `lockfileVersion`, an undecodable key, a key and ident that disagree, unreadable platform metadata, a required edge to an unlocked name. Then this checkout.
- **install-scripts.** Not ported (2.3). The probe that decided it is recorded there.
- **format-coverage.** A glob narrowed to `src/**/*.ts` fails naming a tracked `scripts/x.mjs`. A tracked `.mts` file outside the glob fails. A tracked file that a `.gitignore` or `.prettierignore` entry covers fails (real git and real Prettier in a temporary repository). `echo prettier --check …` gates nothing. A check behind `||`, `;` or a pipe gates nothing. `--ignore-path x` is refused. A `!` or `$` target is refused. `validate` reaching no check fails. A file with no parser counts as not gated. Then this repo.
- **typecheck-coverage.** A tracked file in no program fails by name. An `EXCLUDED` entry that is a pattern, has no reason, is untracked or is now in the program fails. An empty inventory fails. A git failure, a missing compiler, a compiler that exits non-zero or lists nothing each fail. A name containing a newline stays one path.
- **coverage-scope.** A report missing one declared file fails naming it. An `include` that expands to nothing fails. A tracked `.ts` file outside the declaration and outside both lists fails by name. A stale or reasonless entry fails. A missing, empty, non-JSON, symlinked or file-less summary fails. `--prepare` fails on a directory at the summary path.
- **Entry points.** Each new guard with a command line joins the table in `scripts/entry-points.test.mjs`, which runs it through a symlinked checkout and requires its own end-of-run line with the matching exit status. The coverage-scope row runs without `--prepare`, because that harness points at the real checkout.
- **Skill.** `verify:skills` and `verify:skills:cli` pass with nine skills, and the index row exists. No eval result is claimed (2.8). The run command is extracted from the skill file as written and run with `npm` replaced by a stub that exits 17: it must print `EXIT=17` and itself exit 17, and with a stub that exits 0 it must print `EXIT=0` and exit 0. That probe is in the pull request body; it is not a committed test, because a skill body is prose that no runner loads.

## 4. Threat model, accepted limitations, settled decisions

- **Threat model:** a guard that passes while its invariant is broken. The cases: a workflow edit that runs a local-only stage in CI, where `local:dco` reads an `origin/main` the CI checkout does not have (Read, `main.yml` header); a format glob or ignore entry that stops covering a file; a stale `node_modules` that makes green tests say nothing about the lockfile; a dependency whose install script runs with no recorded decision; a TypeScript file that no program and no coverage declaration holds; a guard that reads nothing and passes.
- **Accepted limitations:**
  - `workflow-gate` reads text in executable positions. It evaluates no shell and enters no action. Deliberate obfuscation by someone who can edit a workflow is out of scope: that person can edit the guard in the same pull request, which CI then judges by the edited version (already recorded in the `main.yml` header). A fully opaque `npm run ${{ matrix.script }}` names no family and is not seen.
  - **The guards err toward findings.** Where a decision would need a shell or CLI grammar, the guard reports. Accepted false fails: quoted prose inside `run:` that names a `local:` script; an inline `#` comment that names one (`#` is not a comment in every shell); a format chain using `||`, `;` or a pipe; a custom `--ignore-path`; a Prettier target that is not a plain glob.
  - **`workflow-gate` does not follow a package script into its own commands** (design review r1, finding 1; declined as beyond the source). A workflow that runs `npm run validate` is clean even if `package.json` gained a `prevalidate` that runs a `local:*` script, or if the workflow runs an intermediate script that does. Neither the source's guard nor the reviewed port follows scripts (Measured: neither file reads `package.json` or uses the script-reachability helper). The consequence, should it happen: the sign-off check exits 2 when its base ref is missing (Measured here, with a base that does not exist), which is the case expected on a pull request run, where the default checkout fetches one ref (not verified in CI). On a push to `main` the range is empty and the check passes having checked nothing. So CI goes red on the pull request, or runs an empty check on `main`; it does not merge something wrong. What is lost is the guard naming the cause. A change to `validate`'s own chain is in the diff a reviewer reads.
  - **`workflow-gate` recognizes a local-only stage by its script name, not by the command behind it** (design review r2; declined as beyond the source, the same family as the item above). A step that runs `node scripts/dco-check.mjs --base origin/main` directly is clean, because no `local:*` name appears. The source's rule is name-based, and a command signature would be this repo's own invention; it would also have to tell that step apart from `dco.yml`, which runs the same script on purpose with the pull request's base. The consequence is the one stated above for `local:dco`.
  - **`install-fresh` checks that what the lock requires is installed at the locked version, and nothing else** (design review r1, findings 2 and 3; declined as beyond the source). It does not report a package that is installed and not locked, and it does not compare `package.json`'s declared dependencies with the lock's root. So a hand-installed extra package, or a dependency added to `package.json` without updating the lock, can leave a local run green. Neither reaches `main` that way: CI installs with `--frozen-lockfile`, which refuses a lock that disagrees with the manifest, into a tree that holds no extras. What is lost is the local guard catching it first. Neither the source's guard nor the reviewed port does either check (Measured, by search of both files).
  - **`verify-format-coverage` reads the format script's text, and does not know which Prettier flags stop it checking** (audit r1; declined as beyond the source). A format script written as `prettier --check "<glob>" --help`, or with `--version`, exits 0 having checked no file, and the guard still takes its glob as covered (Measured: Prettier 3.8.4 exits 0 on both). Neither the source's guard nor the reviewed port refuses those flags. It takes an edit to the `format:check` line, which is in the diff a reviewer reads.
  - `install-fresh` trusts each installed copy's own `version`. It reads registry-shaped entries: an npm alias fails closed (key and ident disagree), and a git or tarball entry would be compared by a string that is not a version. This lock has neither (Measured). It cannot fire in CI, which installs fresh.
  - **No guard checks install-time scripts** (2.3). A dependency added later that is on Bun's default list would run its script on a local install with no recorded decision. CI is unaffected (`--ignore-scripts`). A reviewer of a dependency change is the control until the pin moves.
  - The TypeScript inventory drops any path with a segment named like a build-output directory, as the source does. A tracked file under such a directory would leave both inventories. `AGENTS.md` already forbids tracking build output.
  - `coverage-scope` reads an exclude leniently, as the source does: an over-broad exclude makes it expect fewer files.
  - Every measurement here was taken on macOS arm64 with Node 26 and Bun 1.4.4. The first CI run is the first evidence on Linux, Node 22.x and Bun 1.3.14. Read, not verified here: the sibling's CI runs the same files on Node 22.x.
- **Settled decisions:** the source's shape and names wherever they apply. Not-applicable rows are recorded, not built. No new dependency: `yaml`, `prettier`, `typescript` and `vitest` are already `devDependencies`. Guards are `.mjs` under `scripts/`, tested by `node --test` from `test:scripts`. `trustedDependencies` is left undefined until the pinned Bun honors an empty list (2.3). No format exclusion is allowed. `coverage-scope` is limited to the two cases `AGENTS.md` names. A review finding is weighed against NOR-615, and scope expansion is declined with a reason (`AGENTS.md`).
